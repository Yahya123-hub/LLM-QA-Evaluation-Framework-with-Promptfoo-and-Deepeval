# 🧠 1. RAG in YOUR project (not textbook explanation)

RAG = Retrieval Augmented Generation
But in your system, it’s actually:

> “Forcing the LLM to answer using only controlled evidence”

---

## 🔴 Without RAG

```text
User → LLM → answer
```

Problem:

* LLM uses internal knowledge
* hallucinations
* no control over correctness

---

## 🟢 With YOUR RAG system

```text
User Query
   ↓
Retriever (FAISS)
   ↓
Top-K relevant chunks
   ↓
Injected into prompt
   ↓
LLM answers ONLY using that context
```

---

## 🧠 What FAISS is doing (important clarity)

FAISS is NOT “searching documents like Google”.

It does:

### Step 1: Convert text → vectors

```text
"Python is a language" → [0.12, -0.44, ...]
```

(using sentence-transformers)

---

### Step 2: Store vectors in a “geometry space”

Think:

* similar meaning = closer points

---

### Step 3: Query becomes a vector too

Then FAISS does:

> “Find nearest vectors in meaning-space”

---

## 🧠 Why this matters in testing

Because now you control:

* what the model *should know*
* what it *should not know*

So you can test:

### 👉 Faithfulness properly

> Did it stick to retrieved context OR hallucinate?

That’s impossible without RAG.

---

## ⚠️ Critical insight

Your system is NOT testing:

> “Is the LLM smart?”

It is testing:

> “Does the LLM behave correctly under controlled knowledge?”

That’s what makes it a QA system.

---

# 🧪 2. Promptfoo — what it actually does in YOUR system

Promptfoo is NOT an AI evaluator.

It is:

> a RULE ENGINE for LLM outputs

---

## 🔧 Think of Promptfoo as:

```text
If output violates rule → FAIL
```

---

## Example in your project:

### YAML test:

```yaml
assert:
  - type: regex
    value: "Python"
```

---

## What it does at runtime:

1. Takes LLM output
2. Applies rule checks:

   * regex match
   * keyword presence
   * schema validation
3. Pass / Fail only

---

## 🧠 Key point:

Promptfoo does NOT understand meaning.

It only checks:

| Type     | What it checks    |
| -------- | ----------------- |
| regex    | pattern exists    |
| contains | substring exists  |
| schema   | JSON format valid |

---

## 🧠 Why you used it

Because DeepEval alone is:

* probabilistic
* slower
* expensive

Promptfoo gives:

> fast, deterministic guardrails

---

## 🧠 So in your system:

Promptfoo = “hard QA gate”

Example:

* must mention “refund policy”
* must not include profanity
* must follow JSON format

# 🧠 3. DeepEval — what it REALLY is

DeepEval is your:

> “LLM judge system”

But internally it works like this:

---

## Step 1: You give it:

```python
LLMTestCase(
    input=question,
    actual_output=answer,
    retrieval_context=context
)
```

---

## Step 2: DeepEval creates a hidden prompt like:

```text
You are a strict evaluator.

Question: ...
Answer: ...
Context: ...

Score:
- relevance (0–1)
- faithfulness (0–1)
- toxicity (0–1)
```

---

## Step 3: Another LLM (judge model) evaluates it

So actually:

> LLM → LLM judges LLM

---

## 🧠 What each metric really means

### 1. Answer Relevancy

> Does the answer address the question?

Not:

* correct facts

But:

* aligned response

---

### 2. Faithfulness (MOST IMPORTANT IN YOUR PROJECT)

> Did the answer stay inside retrieval context?

This is where your RAG matters.

If your retriever is bad:

* faithfulness drops

If prompt is loose:

* hallucinations increase

---

### 3. Toxicity

> Is output safe?

Uses classification-style judging.
